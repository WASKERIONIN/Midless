## 3. Как устроена логика мира в этом коде

Пайплайн генерации одного чанка 16×16×16 (`Worldgen_Generate`, `server/src/world/worldgen.c:334`):

1. **Заполнение.** Если мод задал `material`-поле — каждый блок вычисляется значением
   Lua-поля в мировых координатах (путь `worldgen.material >= 0`). Иначе работает
   «высотная карта»: на колонку считается смешанная высота по биомам
   (`InitializeTerrainColumn`), затем сверху вниз набирается счётчик `depth` и раскладываются
   `top / filler / stone / underwater`. Скан начинается на `biome->depth + 1` блоков **выше**
   чанка — это «гало», которое делает результат не зависящим от порядка загрузки чанков.
2. **`ApplyMaterialRules`** (`worldgen.c:313`) — правила `define_rule` внутри чанка.
3. **`GenerateOres`** (`worldgen.c:157`) — кластеры/жилы/слои/шум; ячейки-источники
   перебираются с запасом `reach`, поэтому сфера руды дорисовывается и в соседнем чанке.
4. **`GenerateStructures`** (`worldgen.c:262`) — то же: перебор ячеек вокруг чанка +
   обрезка по границе, поэтому структуры на стыке собираются из двух чанков.
5. **`Worldgen_Features`** (`worldgenfeatures.c:113`) — Lua-фичи; кандидаты-«истоки»
   кэшируются на чанк и перебираются с отступом `origin_min/origin_max`.
6. **`Worldgen_SkyMask`** (`worldgen.c:383`) — маска неба. Если задано поле `skylight`,
   колонка сканируется вверх до `ceiling`; иначе либо быстрый путь (чистая высотная карта),
   либо **перегенерация всех чанков выше** до `maxY`.

Кэширование полей (`Worldgen_Eval`, `worldgenfield.c:33`) — мемоизация по «эпохе»
(`evaluationVersion`), поля с флагом `isColumnConstant` переживают смену Y.

генерации; раскладка `top/filler/stone`; дотягиваются ли правила с `offset_y` до соседнего
чанка; стоимость генерации.

## 6. Найденные проблемы

### P1 — подтверждено запуском: `define_rule` с `offset_y` не работает через границу чанка

`server/src/world/worldgen.c:313-329`:

```c
int target = i + rule->dy * CHUNK_SIZE_XZ;
if (target < 0 || target >= CHUNK_SIZE)
    continue;               /* <-- правило молча не применяется */
```

Индексная раскладка `(y*16+z)*16+x`, поэтому `offset_y = ±1` — это `±CHUNK_SIZE_XZ`,
и для блоков в нижнем (`dy<0`) или верхнем (`dy>0`) слое чанка цель уходит за пределы
массива. Соседний чанк об этом не знает: правила применяются только к своему чанку.

Как воспроизведено: `mods/seam64.lua` ставит поверхность ровно на y=64 (это локальный y=0
чанка y=4) и правило `{match = 3 (трава), block = 9, offset_y = -1}`. Результат:
**256 из 256 травяных колонок не получили блок под собой** — на каждом стыке чанков
появляется горизонтальная полоса, где правило не сработало. Тот же мод с высотой 65
(`seam65.lua`, трава на локальном y=1) — 0 пропусков. Так что это именно граница чанка,
а не логика самого правила. Повторяется на сидах 1337 / 7 / 99991.

Ваш `classic_terrain.lua` этим не затронут только случайно: его первое правило
`when = f.lt(256, f.local_index())` и так выключено на локальном y=0. Любое правило вида
«блок под травой» или «блок над рудой» даст видимые полосы каждые 16 блоков.

Лечится прогоном правил по чанку с 1-блочным «гало» сверху и снизу (по образцу того, как
это сделано для `depth` в высотном пути), либо применением правил на стадии, когда соседние
колонки уже известны.

### P2 — по коду + арифметика: draw distance клиента и сервера рассинхронизированы → «граница мира»

* Клиент: ползунок 2…16, значение хранится локально и **никогда не корректируется сервером**
  (`client/src/gui/screens.c:158`; пакета «server → client: draw distance» в
  `client/src/networking/networkhandler.c:52-72` нет).
* Сервер: `serverWorld.maxDrawDistance = 8` (`server/src/world/world.c:66`) и молчаливое
  отсечение `if (distance > serverWorld.maxDrawDistance) distance = serverWorld.maxDrawDistance;`
  (`server/src/packet.c:231`).
* Туман на клиенте считается из **своего** значения: `fogEnd = world.drawDistance * 16 + 8`,
  `fogStart = world.drawDistance * 16 * 0.7 + 8` (`client/src/chunk/chunkmesh.c:106-107`).

При ползунке 16 клиент ждёт чанков до 256 блоков и начинает туман со 188 блоков, а сервер
шлёт чанки только в радиусе `drawDistance + 3 = 11` чанков = 176 блоков
(`server/src/world/chunkmanager.c:51`). Между 176 и 188 блоками — ничем не прикрытая
граница загрузки. Это ровно тот симптом, который в ASCII-части README v35 описан как
«…32… 20-32… maxDrawDistance = 8». В v35 ползунок до 32 — расхождение ещё грубее.

Количество чанков, которое сервер реально стримит (посчитано по формулам из
`chunkmanager.c:42-54`): draw distance 8 → 2533 чанка, 16 → 8997, 32 → 32985.

### P3 — по коду: вертикальная дальность загрузки жёстко зашита в ±4 чанка

`int loadingHeight = fmin(drawDistance, 4);` в трёх местах:
`server/src/player.c:78`, `server/src/world/chunkmanager.c:50`, `client/src/world.c:224`.
То есть по вертикали всегда грузится ±64 блока, сколько бы ни стояло в ползунке, тогда как
горизонтальный радиус растёт до 16 (в v35 — до 32). Для мира с `min_y = -128, max_y = 896`
(`classic_terrain.lua`) это даёт обрезанный сверху и снизу «ломтик»: с горы не видно
подножия, из пещеры не видно небо, а на границе ломтика — резкий срез. Увеличение ползунка
это не лечит.

### P4 — подтверждено отдельным тестом: `hmdel` + прямой обход пропускает чанки

`stb_ds` при удалении переносит **последний** элемент на место удалённого. Проверено
отдельной программой (`tools/worldgen-check` использует тот же `stb_ds.h`): из 10 элементов
при удалении в прямом обходе `for (i = 0; i < hmlen(map); i++)` посещаются только 5,
остальные 5 остаются в таблице.

В `ServerChunkManager_Update` (`server/src/world/chunkmanager.c:240-256`) обход именно
прямой, и внутри вызывается `ServerWorld_RemoveChunk` → `hmdel`. Чанк, переехавший на
освободившийся слот, в этом тике не проверяется: игроку не уходит `UnloadChunk`, пустой
чанк не выгружается. Рядом, в `ServerChunkManager_Shutdown` (`:226`) и в клиентском
`World_Clear` (`client/src/world/world.c:261`), обход обратный — то есть в одном месте
правило нарушено.

### P5 — по коду: `Worldgen_SkyMask` без поля `skylight` перегенерирует все чанки выше

`server/src/world/worldgen.c:448-465`: если у определения мира нет `skylight`, нет быстрого
пути (есть руды/структуры/фичи или непрозрачный грунт не весь), то для каждого чанка
в цикле генерируются **все** чанки от его верха до `maxY` — вместе с рудами и структурами.

Замерено: `tallslow.lua` (maxY=896, руда + деревья, без `skylight`) — 3.3–3.4 мс на чанк
только на маску неба против 0.1 мс у `tall.lua` (то же, но быстрый путь). Штатный
`classic_terrain.lua` задаёт `skylight`, поэтому в него не попадает. При draw distance 8
сервер стримит ~2533 чанка → ~7.4 мс/чанк (замер `classic_terrain.lua`) ≈ **19 секунд
однопоточной генерации** на этом железе. Это вероятная причина «мир грузится/подвисает».

### P6 — мелочи, найденные чтением кода (не исполнялись)

* `server/src/world/worldgen.c:408` — `memset(chunk->skyMask, 0, …)` немедленно
  перезаписывается `memset(…, 255, …)` на строке 411. Мёртвый код.
* `server/src/world/worldgenfeatures.c:42` — `for (int x = -bounds; x < bounds; x++)`:
  сфера асимметрична (охват `-bounds … bounds-1`), центр смещён на полблока.
* `server/src/world/worldgen.c:185` — `reach = size + 2` для жил: при `spacing < size`
  (например `spacing = 8, size = 16`) случайное блуждание может зайти в чанк из
  неперебранной ячейки → жила обрезается по границе чанка. На значениях по умолчанию
  (`spacing = 16, size ≤ 16`) не проявляется.
* Сборка: `server/src/world/worldgenerator.c` включает `FastNoiseLite.h` с `FNL_IMPL`, а
  затем `worldgen.h` тянет тот же заголовок ещё раз — секция реализации лежит **вне** include-guard,
  поэтому текущий `FastNoiseLite.h` из апстрима не компилируется (`redefinition of
  GRADIENTS_2D` и т.д.). Проверено: без `-DMIDLESS_FNL_EXTERNAL` компиляция падает.
  В `tools/worldgen-check` это обходится штатным макросом `MIDLESS_FNL_EXTERNAL`.
* `ChunkData_PackPosition` (`shared/chunkdata.c:20`) пакует координаты в 32 бита
  (`x&4095 << 20 | z&4095 << 8 | y&255`). На Windows `long` 32-битный, сдвиг даёт
  знаковое переполнение (UB), на практике ключи остаются различимыми; при |x| или |z|
  больше 2048 чанков (32768 блоков) возможны коллизии.

## 7. Что проверено и **не** сломано

* Кэширование полей (`isColumnConstant` + эпохи) — расхождений со «свежим» вычислением нет
  ни на одном из 3 сидов, 4096 точек на чанк.
* `skyMask` для `classic_terrain.lua` совпадает с полным перебором поля `skylight`
  во всех 256 колонках.
* RLE-сжатие чанков (`ChunkData_CreateCompressed` / `ChunkData_Decompress`) — round-trip
  точный, буфер не переполняется даже в худшем случае (4096 прогонов = 8192 shorts).
* Генерация **не зависит от порядка** загрузки чанков: 36 чанков, сгенерированных в прямом
  и обратном порядке, совпадают байт-в-байт (включая фичи с кэшем «истоков»).
* Раскладка `top / filler / stone` в высотном пути не зависит от границы чанка
  (≈825 000 точек на прогон).
* `classic_terrain.lua` генерируется детерминированно и воспроизводимо между запусками.

## 8. Что предлагаю сделать дальше (по убыванию пользы)

1. **P2/P3 — одна правка, самый заметный эффект.** Присылать клиенту фактический
   `drawDistance` с сервера (или ограничить ползунок `serverWorld.maxDrawDistance`),
   и заменить `fmin(drawDistance, 4)` на отдельную настройку вертикальной дальности.
   Это убирает «границу мира» и вертикальный срез.
2. **P1** — правила с «гало» на 1 блок по Y (или перенос правил в стадию после заполнения
   соседних колонок). Есть готовый воспроизводящий тест: `tools/worldgen-check/mods/seam64.lua`.
3. **P4** — поменять обход в `ServerChunkManager_Update` на обратный (одна строка).
4. **P5** — не регенерировать чанки выше ради маски неба: либо требовать `skylight` у
   определений с рудами/структурами, либо кэшировать маску неба на колонку.
5. **P6** — почистить мелочи; зафиксировать версию `FastNoiseLite.h` в `/libs`
   или добавить include-guard вокруг секции реализации.

Ни одна из этих правок в этой ветке **не внесена** — только диагностика и инструмент
проверки. Скажите, какие пункты применять, и я сделаю это с прогоном `build.sh` до и после.
